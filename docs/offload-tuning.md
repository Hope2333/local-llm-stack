# 8GB 显存的卸载调优手册

面向「模型装不下，但想要长上下文」的场景。全部结论基于 27B 三元模型（PTQ1_0，5.53 GiB）
在 RTX 4060 Laptop（8GB，272 GB/s）上的实测。

## 先问自己：真的需要那个大模型吗

这是最容易被忽略、收益最大的一步。

| 需求 | 推荐 | 解码速度 |
|---|---|---:|
| 262144 上下文，通用对话 | 9B 全量 GPU | **48.3 tok/s** |
| 262144 上下文，要最快 | 4B 全量 GPU | **78.6 tok/s** |
| 需要 27B 级别的推理质量 | 27B 卸载到 128K | 12.1 tok/s |
| 需要 27B + 极致长上下文 | 27B 卸载到 128K | 12.1 tok/s（上限） |

27B 部分卸载比 9B 全量上卡慢 **4 倍**。只有当评测显示 9B 确实答不对时，才值得为 27B 付这个代价。
模型跑不赢的题，卸载参数也救不了；模型够用的题，小模型全量上卡就是最优解。

## 三种卸载方式，差距巨大

同样 131072 上下文、同样 27B 权重：

| 方式 | 参数 | tg | 显存 | 相对 |
|---|---|---:|---:|---:|
| FFN 下沉 | `-ot 'blk\.(4[0-9]|5[0-9]|6[0-3])\.ffn_.*=CPU'` | **12.11** | 7571 | 1.0x |
| **KV 放内存** | `-nkvo` | 6.38 | 5833 | 0.53x |
| 两者都做 | `-nkvo` + 24 层 FFN | 4.31 | 4559 | 0.36x |

### 为什么 `-nkvo` 这么差

`-nkvo` 把 KV 缓存放在主机内存。但注意力层在 GPU 上运行，
**每生成一个 token 都要把整份 KV 通过 PCIe 读一遍**。

128K 上下文的 KV（q4_0，24 头 / 4 KV 头，64 层）约 1.5 GiB。
PCIe 4.0 x8 实测约 12 GB/s，光搬这 1.5 GiB 就要 125ms，
对应上限 8 tok/s——实测 6.38，吻合。

PCIe 带宽（12 GB/s）只有显存带宽（272 GB/s）的 **4.4%**，
所以任何让热数据反复过 PCIe 的方案都是死路。

### 为什么 `-ot` 下沉 FFN 是对的

`-ot` 把指定层的 FFN 张量放到 CPU，注意力层和 SSM 状态留在 GPU。

- KV 一步都不离开显存
- 每 token 过 PCIe 的只有「该层 FFN 的输入激活」（几 KB 级）
- FFN 占权重 77%，下沉它换来的显存空间最多
- CPU 那部分用 AVX-512 算，本身不慢

代价是 FFN 的计算变成 CPU 的串行瓶颈，所以下沉层数越多越慢（20 层 12.11 vs 24 层 11.21）。

## 参数选择流程

### 1. 先确定 ctx

模型的原生上下文不一定能用满。27B 在 8GB 上的边界：

```
31744 / 32768  → 带 mmproj 时 32768 会断崖
73728          → 不带 mmproj 时的全 GPU 上限
81920          → 能加载但解码 OOM
98304+         → 加载即失败
```

### 2. 去掉不必要的组件

**mmproj 省 848 MiB**，纯文本任务必删。它把全 GPU 的上下文档位从 32768 推到 73728。

### 3. KV 量化

`--cache-type-k q4_0 --cache-type-v q4_0`。

长上下文下这是必需品（2 倍压缩）。质量损失在长上下文场景可以接受；
短上下文（<8K）建议用 `q8_0` 换质量。

### 4. 加卸载层数直到装下

按 `ffn_` 后缀匹配最省事：

```bash
# 从第 40 层起下沉，先试 24 层
--n-gpu-layers 99 -ot 'blk\.(40|41|...|63)\.ffn_.*=CPU'
```

层号从后往前加，因为后面的层对显存的贡献一样但更靠前的位置更容易被后续层访问……实际上差别不大，
从后往前的好处是 `blk\..*` 正则更简单。

实测每层 FFN 约省 55 MiB，同时 tg 掉约 0.4 tok/s。
估算公式：

```
需要的层数 ≈ (当前显存 - 目标余量) / 55 MiB
目标余量建议留 300 MiB 给 compute buffer
```

### 5. 微调 batch

`-ub 1024`（默认 512）在 98304 上下文把 pp 从 195.4 提到 226.6（+16%），
但多吃 240 MiB。**只在显存还有余量时用**，否则直接 OOM。

## 完整对照表

27B PTQ1_0，`-ub` 默认 512，temperature 0，约 1.5K token prompt：

| ctx | 卸载 | pp | tg | 显存 |
|---:|---|---:|---:|---:|
| 65536 | 全 GPU | 144.7 | 25.94 | 7449 |
| 73728 | FFN 7 层 | 246.4 | 20.26 | 7210 |
| 73728 | FFN 10 层 | 238.0 | 18.40 | 7043 |
| 98304 | FFN 12 层 | 195.4 | 16.14 | 7387 |
| 98304 | FFN 12 层 + `-ub 1024` | 226.6 | 17.48 | 7627 |
| 114688 | FFN 16 层 | 191.9 | 15.37 | 7468 |
| 131072 | FFN 20 层 | 183.9 | 12.11 | 7571 |
| 131072 | FFN 24 层 | 179.2 | 11.21 | 7348 |
| 131072 | `-nkvo` | 228.6 | 6.38 | 5833 |
| 131072 | `-nkvo` + FFN 24 层 | 193.9 | 4.31 | 4559 |

注意 pp 反而**随着卸载变高**（144.7 → 246.4）。因为预填充是并行的，CPU 段能吃到多核，
而全 GPU 的 prefill 在 8GB 上受限于 workspace 大小，batch 开不大。
所以卸载的方案「预填充更快、解码更慢」——**长 prompt + 短回答**的任务里它甚至可能更划算。

## 失败排查

| 报错 | 含义 | 处理 |
|---|---|---|
| `failed to allocate Vulkan1 buffer of size N` | 加载期超容 | 降 ctx 或加卸载层 |
| 加载成功但解码 `ErrorOutOfDeviceMemory` | compute buffer 撞墙（断崖） | 降 ctx 一档，或去 mmproj |
| `load_model: failed to load model` | 常是显存被别的后端占着 | 先清显存再试 |
| tg 突然从 26 掉到 6 | 命中断崖 | 见上 |

断崖的判据：**上下文加一档，tg 掉到四分之一**。这不是性能退化，是解码时分配 compute buffer 失败后
Vulkan 后端在别处降级分配。

## 不要做的事

- **不要指望 `-nkvo` 省显存**：它省的是显存，代价是解码掉一半以上
- **不要在 GPU 上开 MTP**：草稿模型吃 2.68 GiB 显存 + 一份带宽，4B 从 78.6 掉到 54.4
- **不要给纯文本任务挂 mmproj**：白吃 848 MiB
- **不要用超过 16 的线程数**：Zen4 双 CCD 抢带宽，24 线程解码只剩 5.16 tok/s
- **不要用 AMD 集显**：610M 只有 2 CU，预填充比 CPU 慢 12 倍

## 激进路线（不适用的场景）

改 llama.cpp 源码做过这些尝试，结论是**不值得**：

- **重写三元 GEMV 内核**：`ggml_vec_dot_ptq1_0_q8_0` 已有 AVX-512 路径
  （`ggml/src/ggml-cpu/arch/x86/quants.c:648`，一次处理 64 个权重），
  实测 144 GFLOPS 已接近 Zen4 解包算力上限，向量化空间很小
- **稀疏 KV / 注意力驱逐**：Qwen3.5 是混合架构（DeltaNet 循环态不可分解），
  驱逐逻辑要重写整个状态管理，收益不确定
- **`--kv-mean-center`**：本 fork 独有参数，需要 `tools/kv-mean-center` 先离线生成
  per-(head, channel) 偏置的 GGUF，能改善 q4_0 KV 的精度但没有速度收益

真正的加速来自**调度策略**（换小模型、下沉 FFN、开 prompt 缓存），不是内核。
